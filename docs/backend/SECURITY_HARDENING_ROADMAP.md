# SECURITY_HARDENING_ROADMAP.md

## 문서 목적
이 문서는 Work Archive의 **보안 개선 로드맵**을 정리한 문서다.

이 문서는 다음 질문에 답한다.
- 현재 보안 상태는 어느 정도인가
- 어떤 부분이 당장 막아야 할 수준의 리스크인가
- 어떤 보안 작업을 지금 하지 않고 뒤로 미뤄도 되는가
- 공개 베타 전 / 공개 후 / 확장 전 단계별로 무엇을 해야 하는가

이 문서는 현재 보안 감사를 완전히 대체하는 문서가 아니라, **제품/백엔드 로드맵에 맞춘 현실적인 보안 강화 계획**을 고정하는 문서다.

---

## 1. 현재 해석

현재 Work Archive의 보안 상태는 아래처럼 해석한다.

### 1-1. 괜찮은 점
- 비밀번호는 해시 저장
- refresh token도 해시 저장
- access token / refresh token 분리
- access token 기반 보호 API 존재
- Works / Sync API는 인증 가드 뒤에 있음
- ValidationPipe 기반의 기본 입력 방어 존재

### 1-2. 약한 점
- 프론트가 access token / refresh token을 `localStorage`에 저장
- refresh token이 HttpOnly cookie 구조가 아님
- 인증/동기화 rate limiting 없음
- CORS 기본 동작이 운영에서 너무 느슨해질 수 있음
- 보안 헤더/helmet 계층 미도입
- Swagger 운영 제한 정책 없음
- 계정 세션 관리와 보안 이벤트 추적이 얕음

### 1-3. 현재 결론
현재 보안은 **개발용/내부 사용 수준으로는 무난하지만, 공개 서비스 기준으로는 운영 보안이 아직 약한 상태**로 본다.

즉,
- 지금 당장 모든 보안 작업을 1순위로 끌어올릴 필요는 없지만
- 공개 베타 전에 반드시 막아야 할 핵심 리스크는 분명히 존재한다.

---

## 2. 로드맵 원칙

### 2-1. 보안은 제품 단계에 맞춰 적용한다
Work Archive는 아직 기능/구조/UX 정리 단계에 있으므로, 보안을 무작정 선행 1순위로 두지 않는다.

### 2-2. 공개 직전에는 최소선이 아니라 실서비스 기준으로 본다
공개 베타 이전에는 아래 3개 축을 반드시 통과해야 한다.
- 세션 탈취 방지
- 인증 abuse 방지
- 운영 노출 최소화

### 2-3. 개인 기록과 공개 데이터는 앞으로 더 분리한다
향후 공개 레이어, 카탈로그, 커뮤니티가 붙으면 보안은 단순 JWT 인증 문제가 아니라 **데이터 경계와 권한 모델** 문제로 확장된다.

---

## 3. 보안 단계 구분

이 로드맵은 아래 4단계로 관리한다.

- Phase 0: 지금 문서로만 고정할 원칙
- Phase 1: 공개 베타 전 필수 보안
- Phase 2: 공개 후 운영 보안 강화
- Phase 3: 공개 확장 전 구조 보안
- Phase 4: 사용자 신뢰를 높이는 보이는 보안

---

## 4. Phase 0 — 지금 바로 고정할 보안 원칙

이 단계는 구현보다 **원칙 합의**가 목적이다.

### 원칙
1. refresh token은 최종적으로 `localStorage`에 두지 않는다.
2. 인증/동기화/계정 API는 공개 전 반드시 rate limit를 건다.
3. 운영에서는 CORS를 명시 화이트리스트로만 연다.
4. Swagger와 디버그성 노출은 운영에서 제한한다.
5. 개인 기록 데이터와 공개 데이터는 앞으로 더 강하게 분리한다.
6. 보안은 “있으면 좋은 것”이 아니라 공개 전 체크리스트 항목으로 관리한다.

### 목적
나중에 보안을 급하게 붙이다가 프론트/백엔드 구조를 다시 뒤엎지 않도록, 지금부터 제품 원칙으로 고정한다.

---

## 5. Phase 1 — 공개 베타 전 필수 보안

이 단계는 **공개 전 반드시 완료해야 하는 최소선**이다.

## 5-1. 토큰 저장 구조 교체
### 목표
refresh token을 `HttpOnly + Secure + SameSite` cookie로 이동한다.

### 해야 할 것
- refresh token을 `localStorage`에서 제거
- refresh API는 cookie 기반 세션 회전 구조로 변경
- access token은 짧게 유지
- 프론트는 refresh token을 직접 읽지 않는 구조로 전환

### 이유
현재 구조에서 가장 큰 리스크는 `localStorage` 기반 세션 탈취 가능성이다.

### 완료 기준
- refresh token이 JS에서 직접 읽히지 않는다
- 로그아웃/만료/refresh UX가 깨지지 않는다

---

## 5-2. CORS 운영 강제
### 목표
운영에서 CORS가 느슨하게 열리는 상황을 제거한다.

### 해야 할 것
- `CORS_ORIGIN`이 비어 있거나 `*`일 때 자동 허용하는 기본 동작 제거
- 로컬 / 스테이징 / 운영 origin 분리
- 운영에서는 명시된 프론트 도메인만 허용

### 완료 기준
- 운영 환경에서 wildcard 허용이 불가능하다
- 배포 문서에 origin 정책이 명시된다

---

## 5-3. 인증/동기화 rate limiting
### 목표
로그인 brute force와 refresh/sync abuse를 막는다.

### 대상 엔드포인트
- `/auth/login`
- `/auth/register`
- `/auth/refresh`
- `/sync/push`
- `/sync/pull`

### 해야 할 것
- IP 기준 제한
- 계정 기준 제한
- 짧은 시간 내 반복 실패 차단
- 실패 누적 시 점진적 지연 또는 임시 제한

### 완료 기준
- 인증 API abuse가 무제한으로 가능하지 않다
- 운영에서 limit 수치 조정이 가능하다

---

## 5-4. 기본 보안 헤더
### 목표
운영 환경의 기본 브라우저 보안 방어선을 추가한다.

### 해야 할 것
- `helmet` 도입
- `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` 등 기본 헤더 적용
- CSP는 처음에는 report-only 또는 완화된 정책으로 시작

### 완료 기준
- 운영 응답에 기본 보안 헤더가 포함된다
- 프론트 렌더링과 API 동작이 깨지지 않는다

---

## 5-5. Swagger 운영 제한
### 목표
운영에서 API 문서가 무분별하게 노출되지 않게 한다.

### 해야 할 것
- 운영에서는 `/docs` 비활성화 또는 제한
- 로컬/스테이징만 기본 공개
- 필요하면 관리자/IP 제한 추가

### 완료 기준
- 운영 공개 도메인에서 Swagger가 기본 노출되지 않는다

---

## 5-6. 공개 베타 전 최종 체크리스트
- [ ] refresh token cookie 전환 완료
- [ ] localStorage refresh token 제거 완료
- [ ] 운영 CORS 화이트리스트 적용 완료
- [ ] auth/sync rate limiting 적용 완료
- [ ] helmet 및 기본 보안 헤더 적용 완료
- [ ] 운영 Swagger 노출 정책 적용 완료

---

## 6. Phase 2 — 공개 후 운영 보안 강화

이 단계는 **사용자가 안심하고 써도 되는 운영 품질**을 높이는 단계다.

## 6-1. 세션 관리 고도화
### 목표
사용자와 운영자가 세션 상태를 더 잘 제어할 수 있게 한다.

### 해야 할 것
- 디바이스/세션 단위 관리
- “현재 기기에서 로그아웃” / “모든 기기에서 로그아웃” 지원
- refresh token `jti` 또는 session table 도입 검토
- 최근 로그인 시간/세션 정보 표시

---

## 6-2. 감사 로그와 보안 이벤트
### 목표
운영자가 계정/인증 관련 이상 상황을 추적할 수 있게 한다.

### 기록 후보
- 로그인 성공/실패
- refresh 실패
- 비정상 sync 실패
- 비밀번호 변경
- 계정 정보 변경
- 공개 범위 변경(향후)

---

## 6-3. 계정 보호 UX
### 목표
보안 상태를 사용자가 이해하고 제어할 수 있게 한다.

### 해야 할 것
- 비밀번호 변경 흐름
- 이메일 변경 검증
- 세션 만료/로그아웃 UX 개선
- 보안 관련 오류 메시지 정리

---

## 6-4. 백업/복구 신뢰성
### 목표
사용자 입장에서 “데이터가 안전하다”는 신뢰를 높인다.

### 해야 할 것
- DB 백업 정책
- 복구 점검
- sync 데이터 손실 방지 정책
- soft delete / rollback 정책 정리

---

## 6-5. 공개 후 운영 체크리스트
- [ ] 세션 관리 개선
- [ ] 보안 이벤트 로그 최소 도입
- [ ] 계정 보호 UX 개선
- [ ] 백업/복구 정책 문서화

---

## 7. Phase 3 — 공개 확장 전 구조 보안

이 단계는 공개 프로필, 커뮤니티, 카탈로그 승격 구조가 붙기 전에 필요하다.

## 7-1. 권한 모델 분리
### 목표
단순 인증 여부를 넘어서 역할 기반 권한으로 확장한다.

### 후보 역할
- 일반 사용자
- 인증 사용자
- trusted editor
- moderator
- admin
- worker/system

---

## 7-2. 공개/비공개 데이터 경계 강화
### 목표
개인 기록과 공개 데이터가 섞이지 않게 한다.

### 해야 할 것
- 개인 기록 read model과 공개 aggregate read model 분리
- review / shortReview visibility 강제
- 공개 프로필/작품 집계 API 분리

---

## 7-3. 제출/수정 abuse 방어
### 목표
카탈로그 승격, 공개 수정, 커뮤니티 입력 남용을 막는다.

### 해야 할 것
- submission quota
- reputation score
- moderation queue
- 이상 패턴 탐지
- 신고/숨김/롤백 구조

---

## 7-4. 파일/이미지 보안
### 목표
업로드/썸네일/이미지 경로를 운영 가능하게 만든다.

### 해야 할 것
- 업로드 파일 타입 검증
- 크기 제한
- 공개 URL 정책 분리
- 외부 이미지 hotlink 정책 검토

---

## 8. Phase 4 — 사용자 신뢰를 높이는 보이는 보안

이 단계는 기술 보안보다 **심리적 신뢰성과 투명성**을 높이는 단계다.

### 해야 할 것
- 개인정보/보안 안내 페이지
- 게스트 모드 vs 계정 모드 차이 설명
- 공개 범위 설명 UI
- 데이터 내보내기/삭제 요청 흐름
- 보안 관련 변경 이력 또는 계정 활동 표시

### 목적
실제로 보안이 좋아도, 사용자가 이해할 수 없으면 안심하지 못한다. 이 단계는 “안전함”을 사용자 경험으로 번역하는 단계다.

---

## 9. 우선순위 요약

## 공개 전 필수
1. refresh token cookie 전환
2. CORS 화이트리스트 강제
3. auth/sync rate limiting
4. helmet 및 기본 보안 헤더
5. Swagger 운영 제한

## 공개 직후 강화
1. 세션 관리
2. 보안 이벤트 로그
3. 계정 보호 UX
4. 백업/복구 신뢰성

## 공개 확장 전
1. 권한 모델 세분화
2. 공개/비공개 데이터 경계 분리
3. moderation / abuse 방어
4. 업로드/이미지 보안

---

## 10. Work Archive 기준 최종 정리

현재 Work Archive는 **보안 전면 투자 단계는 아니지만, 공개 직전에는 반드시 세션 탈취 방지 + 인증 abuse 방지 + 운영 노출 최소화 3축을 완료해야 하는 상태**로 해석한다.

즉,
- 지금은 문서와 설계 원칙을 먼저 고정하고
- 제품/프론트 구조 정리 이후
- 공개 베타 전에 Phase 1을 반드시 완료하며
- 공개 이후 운영/신뢰성/권한 모델로 확장한다.

이 문서는 그 보안 우선순위를 프로젝트 전체 로드맵 안에서 관리하기 위한 기준 문서로 사용한다.
