# COMMERCIAL_WEB_DESIGN_IMPLEMENTATION_PLAN.md

## 목적
이 문서는 Work Archive를 **실제 서비스 수준의 웹 제품**으로 끌어올리기 위한 프론트엔드 웹디자인 구현 계획서다.

기존의 [`FINAL_WEB_DESIGN.md`](./FINAL_WEB_DESIGN.md)가 제품 방향과 최종 디자인 원칙을 정의하는 문서라면, 이 문서는 그 방향을 **실행 가능한 단계, 정보 구조, 화면 우선순위, 컴포넌트 체계, 운영 기준**으로 구체화한 문서다.

이 문서는 다음 문제를 해결하기 위해 작성한다.
- 현재 프론트엔드가 기능은 충분하지만, 상용 서비스 수준의 완성도와 제품 구조가 부족하다.
- 로그인/회원가입만이 아니라 전체 웹 구조가 아직 "개발용 화면"에 가깝다.
- 현재 구현된 구조는 최종 구조가 아니며, 앞으로 추가될 기능과 UX 변화에 대응할 수 있어야 한다.
- 향후 기능 확장, 사용자 증가, 업데이트 주기, 디자인 일관성을 동시에 고려해야 한다.

---

## 1. 목표 정의

### 최종 목표
Work Archive를 다음 조건을 만족하는 상용 수준 웹 서비스로 발전시킨다.

1. **첫인상**이 좋아야 한다.
   - 첫 방문 시 앱 구조와 가치가 직관적으로 이해되어야 한다.
   - 단순 CRUD 도구가 아니라 취향 아카이브 서비스처럼 보여야 한다.

2. **유저 편의성**이 높아야 한다.
   - 기록까지의 진입 장벽이 낮아야 한다.
   - 작품을 찾고, 추가하고, 다시 보는 흐름이 빨라야 한다.
   - 수동 입력보다 가져오기/선택 기반 흐름이 우선되어야 한다.

3. **확장성**이 있어야 한다.
   - 이후 인사이트, 프로필, 공유, 검색 고도화, 추천, 통계, 티어메이커, 커뮤니티 기능이 붙어도 구조가 무너지지 않아야 한다.

4. **업데이트 가능성**이 있어야 한다.
   - 기능이 늘어나도 스타일이 파편화되지 않아야 한다.
   - 화면 단위가 아니라 시스템 단위로 유지보수할 수 있어야 한다.
   - 지금의 정보 구조가 완성형이라고 가정하지 않고, 성장 가능한 구조로 설계해야 한다.

5. **디자인 완성도**가 높아야 한다.
   - 심미성만이 아니라 정보 위계, 시선 흐름, CTA 우선순위, 반응형, 접근성까지 포함해야 한다.

## 2. 설계 전제

이 문서는 다음 전제를 반드시 반영한다.

### 2-1. 현재 구조는 최종 구조가 아니다
현재의 `works`, `sync`, `auth` 중심 구조는 개발 단계에서 기능을 구현하기 위한 구조이며, 최종 제품 구조로 고정해서는 안 된다.

설계 시 다음을 고려해야 한다.
- 상단 내비게이션은 추후 재편될 수 있다.
- 첫 화면은 추후 Home / Discover 중심으로 바뀔 수 있다.
- Sync는 최종적으로 1차 목적 화면이 아니라 지원 기능으로 이동할 수 있다.
- 현재 화면 위계와 메뉴 위치는 서비스 성장에 따라 달라질 수 있다.

### 2-2. 작품 추가는 수동 입력보다 가져오기 중심이 되어야 한다
최종 경험에서 사용자는 제목, 작가, 장르, 썸네일, 설명을 모두 직접 입력하는 방식보다,
**검색 → 선택 → 자동 채움 → 최소 수정**의 흐름을 기본으로 사용해야 한다.

즉, 수동 입력은 예외적 보조 수단이고, 기본 UX는 다음이어야 한다.
1. 검색
2. 외부/내부 메타데이터 후보 표시
3. 작품 선택
4. 자동 채움
5. 상태/별점/한줄평 등 개인 기록만 추가

### 2-3. 티어는 작품 기록의 단순 필드가 아니라 별도 기능으로 확장될 수 있다
현재 데이터 구조상 `tier`는 작품 필드 중 하나로 존재할 수 있지만, 최종 제품 기준으로는 **Tiermaker와 유사한 독립 경험**으로 확장될 가능성이 크다.

따라서 설계 시 다음을 고려해야 한다.
- 작품 상세의 단일 필드로만 티어를 소비하지 않는다.
- 추후 "티어 보드", "티어 편집", "티어 공유", "티어 기반 컬렉션" 기능이 붙을 수 있다.
- 라이브러리와 티어 기능은 연결되지만, 동일 화면/동일 모델로 강하게 묶지 않는다.

### 2-4. 커뮤니티 기능 추가 가능성을 고려해야 한다
현재는 개인 기록 중심 제품이지만, 장기적으로 아래와 같은 기능이 추가될 수 있다.
- 공개 프로필
- 공개 리스트
- 공개 티어표
- 작품별 감상 공유
- 댓글 / 반응 / 좋아요
- 다른 사용자 팔로우

따라서 초기 설계부터 다음 원칙을 지켜야 한다.
- 개인 영역과 공개 영역을 시각적으로 구분할 수 있어야 한다.
- 프로필, 리스트, 티어, 리뷰 화면은 향후 public mode로 확장 가능해야 한다.
- App Shell과 정보 구조가 커뮤니티 기능을 수용할 수 있어야 한다.

### 2-5. 앞으로 추가되거나 바뀔 부분이 많다는 점을 전제로 해야 한다
이 제품은 현재 구조를 영구 구조로 간주하면 안 된다.

설계 원칙은 다음과 같다.
- 오늘의 구현 편의보다 미래의 구조적 유연성을 우선한다.
- 특정 화면에 기능을 과하게 몰아 넣지 않는다.
- 새 기능이 생겼을 때 기존 디자인 시스템 안에서 자연스럽게 수용되도록 한다.

## 3. 참고할 상용 패턴

이 서비스는 아래 유형의 상용 서비스 패턴을 참고하는 것이 적절하다.

### 3-1. 콘텐츠 중심 컬렉션 서비스 패턴
예: 영화/애니/책 아카이브 계열 서비스

배워야 할 점:
- 표지/썸네일이 주인공이어야 한다.
- 컬렉션을 보는 즐거움이 있어야 한다.
- 카드/리스트/필터/정렬 전환이 자연스러워야 한다.

### 3-2. 퍼스널 데이터 대시보드 패턴
예: 생산성 툴, 개인 기록 서비스

배워야 할 점:
- 앱 셸이 조용하고 안정적이어야 한다.
- 사용자가 현재 어디에 있는지 분명해야 한다.
- 정보가 많아져도 질서가 유지되어야 한다.

### 3-3. 서비스형 인증 경험 패턴
예: 상용 SaaS 로그인/회원가입 화면

배워야 할 점:
- 로그인/회원가입은 단순 폼이 아니라 제품 경험의 일부여야 한다.
- 왜 로그인해야 하는지, 어떤 가치를 얻는지 설득력이 있어야 한다.
- 게스트/계정 모드 구분이 자연스러워야 한다.

### 3-4. 기록/통계 서비스 패턴
예: 리포트, 개인 기록 분석, 활동 통계 서비스

배워야 할 점:
- 숫자만 보여주지 말고 해석을 제공해야 한다.
- 재방문 동기를 만드는 요약/인사이트 구조가 필요하다.

### 3-5. 티어메이커 / 사용자 생성 보드 패턴
예: Tiermaker 계열 경험

배워야 할 점:
- 카드 드래그/배치 경험은 일반 CRUD 화면과 다른 상호작용을 필요로 한다.
- 컬렉션과 편집기(보드)는 분리된 맥락으로 설계해야 한다.
- 보기 모드와 만들기 모드를 명확히 분리해야 한다.

### 3-6. 커뮤니티 / 프로필 확장 패턴
예: 공개 프로필, 공개 컬렉션, 피드, 반응 중심 서비스

배워야 할 점:
- 개인 아카이브와 공개 영역은 목적과 분위기가 다르다.
- 공개 화면은 탐색성과 공유성을 갖춰야 한다.
- private mode와 public mode의 전환을 수용할 수 있어야 한다.

## 4. 제품 구조 재정의

현재 구조는 `works`와 `sync`가 너무 전면에 드러나 있으며, 사용자가 서비스에 들어왔을 때 느끼는 경험이 기능 설명 중심에 치우쳐 있다.

이를 다음 구조로 재정렬한다.

### 권장 최상위 IA (현 시점 기준)
- Home
- Library
- Quick Add
- Insights
- Profile
- Settings

### 미래 확장 고려 IA
- Home
- Library
- Quick Add
- Tier Boards
- Insights
- Profile
- Community
- Settings

### 보조 기능
- Sync
- Search
- Session / Account
- Notifications / Toast feedback

### 설계 원칙
1. **Home**이 시작점이 되어야 한다.
2. **Library**는 콘텐츠 중심 컬렉션 뷰어여야 한다.
3. **Quick Add**는 독립된 핵심 흐름으로 강화되어야 한다.
4. **Sync**는 1차 목적이 아니라 지원 기능이어야 한다.
5. **Profile / Insights**는 추후 확장 가능성을 염두에 두고 셸 구조에 미리 고려되어야 한다.
6. **Tier Boards**와 **Community**는 현재 필수 화면은 아니지만, 향후 무리 없이 추가될 수 있도록 IA를 닫힌 구조로 설계하지 않는다.

## 5. 디자인 철학

### 핵심 철학
- Content First
- Fast Capture
- Calm Premium
- Personal Archive
- Systematic Consistency
- Expansion Ready

### 한 문장 정의
Work Archive는 단순한 기록 도구가 아니라, 사용자의 감상 취향과 소비 흐름을 정리해주는 **개인 미디어 아카이브 서비스**이자, 추후 **티어 제작과 커뮤니티 확장까지 수용 가능한 플랫폼**처럼 보여야 한다.

### 피해야 할 방향
- 관리자 패널 같은 인상
- 과한 글래스모피즘 남발
- 화면마다 다른 톤
- 설명이 많은 기술형 UI
- 기능은 많지만 "무엇을 해야 할지"가 안 보이는 구조
- 현재의 임시 구현 구조를 최종 구조처럼 고정하는 설계

## 6. 브랜드 및 비주얼 전략

### 브랜드 성격
- 차분함
- 정돈감
- 프리미엄
- 개인화
- 취향 존중
- 확장 가능한 플랫폼 느낌

### 비주얼 방향
- 다크 테마 유지
- 채도 낮은 블루/바이올렛 강조색 사용

- 여백을 적극적으로 사용
- 과한 장식 대신 구조적 완성도에 집중
- 일반 아카이브 화면과 보드형/커뮤니티형 화면이 추후 공존 가능하도록 기본 시스템을 단단히 만든다.

### 톤 앤 매너
- 한국어 UI 기준
- 짧고 매끄러운 서비스형 카피
- 기술 용어 최소화
- 사용자의 행동과 목적을 중심으로 메시지 작성

## 7. 화면 구조 전략

## 7-1. Home

### 목표
- 첫 방문과 재방문 모두에서 제품 가치를 즉시 전달한다.
- 사용자가 무엇을 해야 하는지 바로 이해할 수 있게 한다.
- 최근 기록, 빠른 추가, 요약 정보, 추천 행동을 보여준다.
- 향후 공개 프로필, 티어 보드, 인사이트로 자연스럽게 확장되는 중심 허브가 된다.

### 포함할 핵심 섹션
1. Hero Search / Quick Add
2. 최근 기록한 작품
3. 진행 중 / 다시 보기 추천
4. 이번 달 통계 요약
5. 최근 활동
6. 향후 추천 섹션 / 공개 콘텐츠 / 티어 요약 배치 가능 공간

### 구현 원칙
- Home은 설명 페이지가 아니라 **행동 시작점**이어야 한다.
- 상단에서 검색과 빠른 추가가 가능해야 한다.
- 모바일에서도 바로 이해 가능해야 한다.
- 이후 커뮤니티 요소가 추가되어도 구조가 무너지지 않게 섹션형 레이아웃으로 설계한다.

---

## 7-2. Library

### 목표
- 사용자의 전체 기록을 가장 효율적으로 탐색할 수 있는 화면
- 컬렉션을 보는 즐거움을 주는 화면
- 최종적으로는 개인 라이브러리와 가져오기 기반 작품 등록 흐름을 자연스럽게 연결하는 화면

### 필수 구조
- 상단: 검색 / 정렬 / 보기 전환
- 좌측 또는 접이식 패널: 필터
- 본문: 작품 카드 / 리스트

### 보기 모드
- Grid View
- Compact View
- List View

### 핵심 디자인 방향
- 작품 카드가 더 콘텐츠 중심으로 보이게 한다.
- 텍스트보다 표지와 핵심 상태를 먼저 보여준다.
- 필터와 컨트롤은 강하지만 시각적으로 과하지 않게 한다.
- 나중에 "가져온 작품", "미분류", "내 컬렉션", "공개 컬렉션" 같은 구분이 붙어도 구조를 유지할 수 있어야 한다.

---

## 7-3. Work Detail

### 목표
- 작품과 개인 기록을 한 화면에서 가장 잘 보여주는 핵심 페이지
- 최종적으로는 메타데이터, 개인 감상, 티어 연동, 공개 여부, 커뮤니티 반응까지 확장 가능한 구조를 가진다.

### 위계
1. 작품 표지
2. 제목 / 타입 / 상태 / 별점 / 티어 연동 상태
3. 한줄평
4. 리뷰
5. 메타 정보
6. 액션 (수정 / 삭제 / 티어 보드에 추가 / 공개 설정 등 미래 확장)

### 개선 원칙
- 지금보다 작품 자체가 훨씬 강하게 보여야 한다.
- 메타 정보는 1차 정보가 아니라 보조 정보로 내려야 한다.
- 개인 감상 기록이 더 풍부하게 보여야 한다.
- 미래 확장 영역(예: 티어 보드, 공개 리뷰, 커뮤니티 반응)을 위한 슬롯을 염두에 둔다.

---

## 7-4. Quick Add / Create / Edit

### 목표
- 기록 입력의 허들을 가장 낮춘다.
- 최종적으로는 수동 입력보다 가져오기 기반 경험을 기본으로 한다.

### 원칙
- Quick Add는 빠른 입력용, Edit는 상세 편집용 역할을 분리한다.
- 긴 폼을 처음부터 전부 보여주지 않는다.
- 검색 기반 구조를 우선한다.
- 수동 입력은 예외적 보조 수단으로 남긴다.

### 이상적인 단계
1. 검색
2. 후보 선택
3. 외부/내부 메타데이터 자동 채움
4. 상태 / 별점 / 한줄평
5. 저장
6. 필요 시 고급 편집

### 구현 포인트
- 저장 전까지의 클릭 수 최소화
- 키보드 사용성 강화
- 입력 필드 간 시각적 위계 강화
- 나중에 여러 데이터 소스(내부 캐시, 외부 검색, 커뮤니티 추천)가 붙어도 구조를 바꾸지 않도록 검색/후보/선택/확정 흐름을 명확히 분리한다.

## 7-5. Auth (로그인/회원가입)

### 목표
- 단순 폼 페이지가 아니라 서비스의 정체성을 보여주는 인증 경험
- 향후 공개 프로필, 커뮤니티, 계정 동기화 가치까지 연결되는 진입점이 된다.

### 구조 방향
- 데스크톱: 2단 레이아웃
  - 좌측: 가치 제안 / 기능 요약 / 게스트 모드 안내 / 향후 확장 가치
  - 우측: 인증 카드
- 모바일: 단일 컬럼 + 정보 밀도 축소

### 핵심 메시지
- 게스트 모드는 유지된다.
- 로그인하면 동기화와 계정 아카이브를 사용할 수 있다.
- 개인 기록을 더 안정적으로 관리할 수 있다.
- 향후 공개 프로필, 티어 공유, 커뮤니티 기능과 연결될 수 있다.

### 피해야 할 것
- 히어로 아래에 폼만 하나 덩그러니 놓는 구성
- 입력창 2개 + 버튼 1개 수준의 밋밋한 화면

---

## 7-6. Sync

### 목표
- 기술 기능을 사용자 친화적으로 표현한다.
- 계정 기능, 작품 가져오기, 공개 기능과 공존 가능한 지원 기능으로 유지한다.

### 위치 전략
- 1차 목적 메뉴가 아니라 보조 기능으로 배치한다.
- 계정 모드에서만 유의미한 기능임을 자연스럽게 설명한다.

### 시각 전략
- 상태 요약
- 최근 실행 결과
- 대기열
- 충돌

### UX 전략
- 너무 개발자 도구처럼 보여서는 안 된다.
- 메시지는 짧고 이해 가능해야 한다.
- 미래에 자동 동기화나 공개 동기화가 추가되어도 현재 구조를 크게 깨지 않도록 설계한다.

---

## 7-7. Tier Boards (추후 핵심 확장)

### 목표
- 단순 작품 필드가 아니라, 사용자가 작품들을 보드 형태로 배치하고 정리하고 공유할 수 있는 독립 기능

### 원칙
- 라이브러리의 하위 필드가 아니라 별도 경험으로 설계한다.
- 보기 모드와 편집 모드를 분리한다.
- 드래그 앤 드롭 상호작용을 염두에 두고 일반 CRUD 레이아웃과 분리한다.

### 미래 기능 예시
- 내 티어 보드 생성
- 보드별 주제 설정
- 작품 추가/제외
- 공개 링크 공유
- 커뮤니티 반응

---

## 7-8. Insights / Profile / Community (추후 핵심 확장)

### Insights 목표
- 사용자가 다시 방문하고 싶은 이유를 만든다.
- 단순 통계가 아니라 취향 해석을 제공한다.

### Profile 목표
- 자기 표현과 공유 가능성을 제공한다.
- 개인 페이지가 서비스 가치를 확장시킨다.

### Community 목표
- 개인 기록 서비스에서 공개 경험으로 확장될 수 있는 공간을 만든다.
- 공개 리스트, 공개 티어, 반응, 댓글, 팔로우 등으로 확장 가능해야 한다.

### 왜 미리 고려해야 하는가
- 추후 추가할 화면이 셸과 내비게이션 구조에 자연스럽게 들어가야 한다.
- 지금부터 공간과 위계를 염두에 두지 않으면, 나중에 억지로 끼워 넣게 된다.
- private mode와 public mode가 자연스럽게 공존해야 한다.

- 현재 구조를 고정된 완성형으로 간주하지 않는다.

## Phase C. 서비스 가치 확장
목표: 재방문 이유를 만들고 미래 확장 기능을 준비한다.

- 티어 보드와 공개 프로필이 자연스럽게 들어갈 수 있다.

## Phase D. 공개형 확장 / 커뮤니티 준비
목표: 개인 기록 중심 앱에서 공개/공유 가능한 서비스 구조로 확장 준비를 한다.

- 공개 프로필 페이지 설계
- 공개 리스트 / 공개 티어 보드 페이지 설계

- 개인 영역과 공개 영역의 셸/카드 차이 정리

### 완료 기준
- private archive와 public/community layer가 충돌 없이 공존할 수 있다.
- 미래 기능 추가 시 구조 재붕괴 없이 확장 가능하다.

- QA 체크리스트 운영

- 화면 간 톤 차이가 줄어든다.
- 잔여 영어/기술 용어가 제거된다.

- 하나의 화면을 고칠 때 전체 IA에 미치는 영향을 검토한다.
- 미래 기능(Tier Boards, Community, Import UX)이 들어올 자리를 항상 고려한다.

### 업데이트 우선순위 원칙
1. 사용자 경험에 직접적인 영향이 큰 것
2. 구조적 문제를 해결하는 것
3. 반복 유지보수 비용을 줄이는 것
4. 장식보다 가독성과 탐색성을 높이는 것
5. 미래 기능과의 충돌 가능성을 줄이는 것

## 15. 최종 정의

Work Archive의 웹디자인은 단순히 "다크 테마의 예쁜 기록 앱"이 되어서는 안 된다.

최종적으로는 다음과 같아야 한다.
- 첫 방문 시 무엇을 할 수 있는지 명확하고
- 작품을 보는 재미가 있으며
- 기록이 빠르고
- 다시 찾아오기 쉬우며
- 작품은 수동 입력보다 가져오기 기반으로 빠르게 등록할 수 있고
- 향후 티어 보드, 통계, 공유, 공개 프로필, 커뮤니티 기능이 자연스럽게 연결되며
- 기능이 늘어나도 구조가 무너지지 않는

**실제 서비스 수준의 개인 미디어 아카이브 플랫폼**

이 문서는 그 목표를 달성하기 위한 구현 계획 기준 문서로 사용한다.
